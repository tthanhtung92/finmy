# ADR-0018: Self-hosted deployment shape: in-cluster data tier, SOPS-encrypted secrets, Helm-on-tag CD

## Status

Accepted, 2026-08-05.

## Context

`docs/ROADMAP.md` section 5's Phase 5 paragraph asks for a Helm chart, k3s on a VPS with an ingress controller and cert-manager, Terraform for the server/DNS/firewall, encrypted secrets, a decision on where Postgres/Redis/MinIO run, and continuous deployment on tag. Before this phase there was no Helm chart, no Terraform, no k3s manifests and no secret-encryption tooling anywhere in the repo, greenfield like Phase 4's observability stack. Two tracked debts close here: TECH-DEBT #15 (`docker/docker-compose.yml`'s inline development `Jwt__SigningKey`) and TECH-DEBT #4 (Wolverine auto-creating its storage tables at startup).

No VPS exists yet. Everything Terraform touches is written and validated (`terraform validate` against real provider schemas) but never applied; the chart is validated the same way, with `helm lint` and `helm template` piped through `kubeconform`, since no cluster exists to `helm install` against either. This ADR records the shape chosen so the eventual first real deploy has a design to follow rather than one to invent under pressure.

## Options considered

**Data tier: Postgres, Redis and MinIO in-cluster on local-path volumes, versus CloudNativePG for Postgres, versus fully managed services.** A single Hetzner `cx22` is the whole budget for this project; a managed Postgres instance alone typically costs more per month than the entire server. CloudNativePG gives real point-in-time recovery and failover primitives, but a second operator's control loop on a single-node cluster is a second thing to understand and upgrade for a database with exactly one replica regardless. Chosen: plain `StatefulSet`s on `local-path` (k3s's bundled default storage class), with a nightly `pg_dump` `CronJob` as the only backup mechanism. This is the honest floor, not a stopgap dressed up as more: the recovery point objective is one night, and restoring from it is a manual `pg_dump`/`pg_restore` step, not an automated failover. Redis stays a `Deployment`, not a `StatefulSet`: it is HybridCache's L2 layer only, so losing it on a restart is a cold cache, not data loss.

**Migration and Wolverine `resources setup` ordering: a Helm `pre-install`/`post-install` hook, versus a plain `Job` applied alongside everything else.** A `pre-install` hook blocks the whole release before the Postgres `StatefulSet` in the same chart has even been created, so a fresh cluster deadlocks waiting for a database that does not exist yet. A `post-install` hook run under `--wait` never fires, because Helm is already blocked waiting for the Deployment's rollout to report Ready, which cannot happen until migrations land: the same deadlock from the other side. A plain, non-hook `Job` (`deploy/helm/finmy/templates/migrate-job.yaml`) sidesteps both: everything is submitted to the API server together, the Job retries under its own `backoffLimit` until Postgres accepts connections, and the API's replicas simply fail `/health/ready` (which already checks `GetPendingMigrationsAsync` per ADR-0014) until the Job succeeds. ADR-0014 already put the safety in the readiness gate, not in ordering; this decision just gives that gate a Kubernetes-native trigger to gate against. The Job's name includes `{{ .Release.Revision }}` because Jobs are otherwise immutable across an image-tag change on `helm upgrade`.

**Secrets: SOPS + age, versus Sealed Secrets, versus a cloud KMS.** Sealed Secrets binds encryption to the cluster's own controller key, so a value can only be authored against a cluster that already exists, and losing or rebuilding the cluster means re-sealing every secret from scratch. SOPS with age keeps the encryption key outside the cluster entirely: the same encrypted file can be authored, reviewed and decrypted with no cluster running at all, which matches this phase's reality of writing the whole deploy path with no cluster to test it against. A cloud KMS (age has a plugin story for this) is one more account and API surface for a single-server deploy with one secret file. Chosen: SOPS + age, one encrypted values file (`deploy/values-prod.sops.yaml`) holding only the four values `values.yaml` cannot ship a real default for: `Jwt__SigningKey`, the Postgres password, and the MinIO root credentials. The age private key lives in one GitHub Actions secret and the owner's password manager, never in the repository.

**Continuous deployment: GitHub Actions on tag running `helm upgrade`, versus Argo CD.** Argo CD's pull-based reconciliation and drift detection earn their keep once there is more than one environment or more than one cluster to keep converged; today there is one cluster, one release, and one writer. Standing up Argo CD now means securing and upgrading a second always-on service on the same single node the application itself runs on, for a workflow Actions already does in eleven lines. Chosen: extend `release.yml`'s existing tag-triggered `publish` job with a `deploy` job gated on a `DEPLOY_ENABLED` repository variable, so tagging a release does not fail red while no cluster exists to deploy to.

**Ingress controller: k3s's bundled Traefik, versus installing ingress-nginx.** k3s ships Traefik enabled by default; not disabling it removes an install step for a single-app deployment with no multi-controller requirement. Chosen: Traefik, left at its k3s default.

## Decision

Postgres, Redis and MinIO run in-cluster as plain `StatefulSet`s (Redis as a `Deployment`) on k3s's `local-path` storage class, backed up nightly by a `pg_dump`-based `CronJob`. Wolverine's `resources setup` and the three modules' EF migrations run from a single non-hook `Job`, applied in the same `helm upgrade --install --wait` as everything else, with the API's `RollingUpdate` strategy set to `maxUnavailable: 0` so old replicas keep serving while new ones wait on that Job behind the readiness gate. Production secrets are encrypted with SOPS and age in `deploy/values-prod.sops.yaml`, decrypted only inside the GitHub Actions `deploy` job. Deployment is `release.yml`'s tag-triggered `deploy` job running `helm upgrade`, inert until `DEPLOY_ENABLED` is set. Terraform provisions one Hetzner `cx22`, a firewall, and DNS records, with k3s and cert-manager installed through the server's own cloud-init rather than a separate Ansible or Helm-from-a-workstation step: written and `terraform validate`-clean, not yet applied.

## Consequences

The whole data tier's durability rests on one server's one disk plus whatever the nightly `pg_dump` CronJob happens to have captured; disk loss between two nightly runs loses that window's writes outright, and restoring is a manual operation, not a tested runbook. This is the honest starting point for a single-user self-hosted deploy, not a permanent one: CloudNativePG or a managed Postgres both remain available upgrades the moment the data stops being disposable at that cost.

Nothing in this ADR has run against a live cluster. `helm lint`, `helm template` piped through `kubeconform`, and `terraform validate` confirm syntax and schema; they confirm nothing about whether the migrate Job's retry budget survives a first-boot `local-path` PVC provisioning window, whether cert-manager's CRDs are in place before the `ClusterIssuer` manifest that depends on them, or whether Let's Encrypt's HTTP-01 challenge succeeds against a DNS record Terraform just created. The first real `terraform apply` and the first real tagged deploy are where these get found, not this phase.

TECH-DEBT #15 closes: the compose file's inline `Jwt__SigningKey` default stays exactly what it always was, a local-development convenience, and is no longer standing in for a real secret-management story anywhere. TECH-DEBT #4 closes: production sets `JasperFx.Profile.ResourceAutoCreate = AutoCreate.None` (`Program.cs`'s existing `CritterStackDefaults` call, next to `GeneratedCodeMode`), so the `wolverine` schema comes from the explicit `resources setup` step this ADR's migrate Job runs, not from a race between replicas at startup.
