# ADR-0017: Observability is OTLP-first, with a shared ActivitySource in SharedKernel and alerting provisioned in Grafana

## Status

Accepted, 2026-08-05.

## Context

`docs/ROADMAP.md` section 5's Phase 4 paragraph calls for Serilog structured logging with correlation and trace ids, full OpenTelemetry tracing and metrics across ASP.NET Core, HttpClient, Npgsql, Redis and Wolverine, a self-hosted collector into Prometheus, Tempo, Loki and Grafana, a dedicated `ActivitySource` for the anti-overspend path, and dashboards and alerts on error rate, p95 latency, outbox backlog and concurrency conflicts. Before this phase there was no Serilog or OpenTelemetry package anywhere in `Directory.Packages.props`, no `ActivitySource`, and no `Meter`: this was greenfield, not an extension of partial setup.

Two constraints from the existing architecture shaped the design. The module boundary rule (`CLAUDE.md`) means a cross-cutting concern like tracing has to be wired from the host or a shared project, not by one module reaching into another. And Wolverine's codegen constructs each handler's `DbContext` inline in the handler body with no `CreateScope()` (documented in `docs/TECH-DEBT.md`'s "Notes worth keeping" section), so any context-propagation mechanism assuming ambient DI scope, such as `IHttpContextAccessor`-style state, cannot be trusted inside a handler; `Activity.Current`, an `AsyncLocal`, has no such dependency and was confirmed by inspecting Wolverine's generated handler wrappers (`codegen preview`) to already carry the trace across message dispatch on its own.

## Options considered

**Metrics export: OTLP push to the collector, versus the app exposing `/metrics` for Prometheus to scrape directly.** A scrape endpoint is one HTTP hop shorter, but it is a new public route, which under ADR-0016's authenticated-by-default fallback policy would need `.AllowAnonymous().DisableRateLimiting()`, the same treatment as the health endpoints, just to let an internal service reach it. OTLP push means Prometheus never talks to the app at all; it scrapes the collector's own re-exposed endpoint instead. Chosen: OTLP push, so the app's authorization surface does not grow for an operational concern.

**Logs to Loki: a Serilog sink writing OTLP straight to the collector, versus a filelog/Promtail (or Grafana Alloy) sidecar tailing container stdout.** Tailing stdout needs no new package on the app side, but it needs a host bind-mount to the Docker log directory, behaves differently again once this moves to Kubernetes in Phase 5, and would need every field the tailer parses back out of a JSON line rather than getting them as structured attributes. `Serilog.Sinks.OpenTelemetry` sends structured log records directly, so `trace_id` and `correlation_id` arrive as attributes Loki can filter and join on, not substrings of a message. Chosen: a dual sink, `Serilog.Sinks.Console` writing compact JSON to stdout always (so `docker compose logs` stays useful with no collector running), plus `Serilog.Sinks.OpenTelemetry` to the collector only when `OpenTelemetry:OtlpEndpoint` is configured.

**Where the anti-overspend `ActivitySource` and `Meter` live: a new shared observability project, one source per module, or `Finmy.SharedKernel`.** A new project is a real option but adds a project and a reference edge for three static fields. One source per module would mean Ledger's and Budgeting's spans for the same transaction come from two different sources, which is a harder join in a query than it needs to be given they already share one trace by way of Wolverine's own propagation. `Finmy.SharedKernel` already holds cross-cutting primitives (`Result<T>`, domain-event base types) and both modules' Application layers already reference it, so it crosses no boundary. Chosen: `Finmy.SharedKernel.Observability.FinmyTelemetry`, one `ActivitySource` (`Finmy.AntiOverspend`) and one `Meter` (`Finmy`) for the whole anti-overspend path.

**Alerting: Grafana's own unified alerting, versus a Prometheus Alertmanager container.** Alertmanager is the more conventional choice ahead of Kubernetes, and it can only query Prometheus, while this deploy also wants an outbox-backlog panel and, later, log-based alerts. Grafana's unified alerting can query any provisioned datasource and needs no sixth container. Against a single-user self-hosted deploy with no notification target decided yet, standing up Alertmanager now would mean provisioning routing and receivers for a destination that does not exist. Chosen: Grafana unified alerting, provisioned as YAML under `docker/observability/grafana/provisioning/alerting/`, routed through Grafana's built-in default notification policy with no explicit contact point. Revisit once Phase 5 picks a real destination (email, webhook) for this single-user deploy.

## Decision

The app exports traces and metrics over OTLP only, gated on `OpenTelemetry:OtlpEndpoint` being non-empty in configuration; with it blank, `ObservabilityExtensions.AddObservability` still wires in-process instrumentation (ASP.NET Core, HttpClient, Npgsql, Redis, Wolverine, and `FinmyTelemetry`'s sources) but adds no exporter, so a bare `dotnet run` or the test suite never spends a flush interval failing to connect to a collector that is not running. `Serilog.Sinks.OpenTelemetry` is gated the same way, sharing the same configuration key.

`FinmyTelemetry` (`src/Shared/Finmy.SharedKernel/Observability/FinmyTelemetry.cs`) exposes the `Finmy.AntiOverspend` `ActivitySource` and the `Finmy` `Meter`. Four handlers each open one span: `RecordTransactionHandler` (`ledger.record_transaction`), `TransactionPostedHandler` (`budgeting.apply_transaction`), `EnvelopeOverspentHandler` (`ledger.reverse_transaction`) and `TransactionConfirmedHandler` (`ledger.confirm_transaction`), each tagged with `transaction.id` and, where relevant, `envelope.id` and an `outcome`. Because Wolverine already propagates trace context across message dispatch, these spans nest inside the same trace as the originating HTTP request without any extra plumbing; this was confirmed against a live collector, where a single overspending `POST /api/v1/transactions` produced one trace in Tempo containing the ASP.NET Core span, both Ledger spans and the Budgeting span, joined to the Npgsql client spans Wolverine's own generated handler code also participates in.

Three counters live on the same `Meter`: `finmy.transactions.recorded`, `finmy.envelopes.overspent`, and `finmy.envelope.concurrency_conflicts`. An `ObservableGauge`, `finmy.outbox.backlog`, is published by a new background service, `OutboxBacklogMetrics`, which polls `wolverine.wolverine_outgoing_envelopes`'s row count every 15 seconds and hands the callback a cached value, since an `ObservableGauge` callback must be synchronous and the count is not cheap enough to run inline on every export tick.

`CorrelationIdMiddleware`, registered first in the pipeline, accepts an inbound `X-Correlation-ID`, generates one when absent, stamps it on the current `Activity` as a `correlation.id` tag, and echoes it on the response. `ActivityEnricher` reads that tag (falling back to the trace id when absent) plus `trace_id` and `span_id` off `Activity.Current`, and adds all three to every Serilog log event.

The Grafana dashboard (`finmy-overview.json`) and the four alert rules (error rate, p95 latency, outbox backlog, concurrency conflicts) are provisioned as code under `docker/observability/`, in a separate `docker/docker-compose.observability.yml` that adds Prometheus, Tempo, Loki, Grafana and an OpenTelemetry Collector without touching `docker/docker-compose.yml`.

## Consequences

The correlation id set by `CorrelationIdMiddleware` lives on the HTTP request's own span. Wolverine's message-handling spans belong to the same trace and so share the correct `trace_id`, but they do not inherit the `correlation.id` tag, so log lines from inside a handler carry the right trace id for joining in Tempo or Loki but fall back to the trace id, not the caller-supplied correlation id, for the `correlation_id` field. The trace id is the reliable cross-module key; propagating the human-supplied correlation id into message handlers as well would need Wolverine message headers or baggage, deliberately left undone this phase.

`finmy.envelope.concurrency_conflicts` only counts conflicts caught in `EnvelopeRepository.SaveChangesAsync`, which is the HTTP CRUD path. On the message path, `AutoApplyTransactions()` saves after `TransactionPostedHandler` returns, so a concurrency conflict there is caught by Wolverine's own host-level retry policy in `Program.cs` and never reaches this counter. The "Concurrency conflicts" dashboard panel and its alert rule are both annotated with this gap so the numbers are not read as more complete than they are; closing it would mean either moving the save inside the handler's own try/catch, which conflicts with how `AutoApplyTransactions()` is meant to be used, or asking Wolverine for its own failure metric by exception type, not yet confirmed to exist under a stable name.

Every new package (`Serilog.AspNetCore`, `Serilog.Sinks.OpenTelemetry`, `Serilog.Formatting.Compact`, the `OpenTelemetry.*` instrumentation and exporter packages, `StackExchange.Redis`) is MIT or Apache-2.0 licensed and checked against `BannedLibraryTests.cs`'s list, which flags none of them. `StackExchange.Redis` is pinned directly at `2.13.17` on the 2.x line rather than the newer 3.x rewrite, since `Microsoft.Extensions.Caching.StackExchangeRedis` only requires `>= 2.7.27` and the Redis trace instrumentation package targets the 2.x API; `HybridCache`'s L2 and the trace instrumentation now share one `IConnectionMultiplexer` built once at startup instead of each connecting independently.
